# /ask-codex

## 背景

Claude Code 当前所在沙箱**不能直连 `api.openai.com`**（403 Host not in allowlist），所以 codex CLI 跑不起来。但用户本机终端可以。

这个 skill 的任务是**最小化用户的复制粘贴负担**：把要问的内容打磨成一段精炼 prompt，输出**一行可粘贴的 `codex exec` 命令**，并清楚告诉用户「运行 → 把回答贴回来」。

## 何时触发

只要用户表达任意以下意图就触发：
- "问问 Codex"、"跟 codex 讨论"、"问 GPT"
- "让 codex 评审 / red team / 红队"
- "ask codex"、"codex review"、"second opinion"
- 任何"我想拿一个独立模型的意见"的语境

## 工作流

### 1. 明确问题

如果用户已经给了具体问题，直接进入第 2 步。

如果用户只说"问问 codex"没说具体问什么，反问一句：「你想让 codex 评审 / 验证什么？是上面的方案、最近的代码、还是别的？」

### 2. 选择模式

按问题类型挑一个 preset，决定 prompt 风格：

| 模式 | 何时用 | prompt 风格 |
|---|---|---|
| **second-opinion** | 用户问"这个方案合理吗" | "请独立判断 X 是否合理，重点指出我可能忽略的问题或更好选择" |
| **red-team** | 用户想找漏洞 | "扮演挑剔的评审，列出 X 方案里**最有可能翻车**的 3 个点" |
| **code-review** | 涉及具体代码 | 把代码块嵌进 prompt，要求"指出 bug、性能问题、可维护性问题" |
| **factcheck** | 用户怀疑某个事实 / 价格 / 数字 | "请核实下面陈述：X。如有错给出更可靠的来源数字" |
| **brainstorm** | 用户要替代方案 | "给我 3 个完全不同方向的方案 + 各自最大缺点" |

不确定就用 **second-opinion**。

### 3. 写 prompt

约束：
- **300 字以内中文**（codex 默认是英文，但中文回答方便用户阅读）
- **结构化要求**：让它列出"赞同/分歧/补充"三段，或"风险点 1/2/3"
- **避免歧义**：把上下文（什么项目、当前选型、目的）放进去，不要假设 codex 知道
- **明确给出"你已经考虑过 X"**，让它跳过这些点

### 4. 输出命令

输出格式（**严格**）：

````markdown
你本地终端跑这一行：

```bash
codex exec "<填好的 prompt>"
```

跑完把整段回答贴回来，我对照修正。
````

如果 prompt 太长（>500 字符），改用 heredoc 形式：

```bash
codex exec "$(cat <<'EOF'
<多行 prompt>
EOF
)"
```

### 5. 收到用户的回贴后

- 逐条对比 codex 的观点和当前方案
- 三档分类：**赞同 → 维持**、**分歧 → 重新评估、给出我的判断**、**补充 → 决定要不要采纳**
- 如果 codex 提出的是事实性更正（价格、API 行为），优先采信，但用 WebSearch 二次验证再改代码
- 不要因为 codex 说了什么就盲目改，**保持 Claude 的独立判断**

## 不要做的事

- ❌ 不要伪装成已经"问过 codex"——明确告诉用户必须自己跑
- ❌ 不要尝试在沙箱里再 `codex exec` —— 已知 403，浪费时间
- ❌ 不要把 prompt 拆成多个命令让用户跑多次（除非确实需要分阶段）
- ❌ 不要在 prompt 里塞 API key、token、私密内容

## 用户调用形式

- `/ask-codex 你怎么看 X 方案`
- "问问 codex 这个方案"
- "让 codex 评审一下这段代码"
- "拿 codex 的意见对比一下"
